# 阶段五外部成本与场景覆盖估算 V1

_日期：2026-08-24；性质：公开资料锚点 + 显式假设的预估，不是实车实测、不构成行业统计。_

## 结论先行

计划书中的三个数字目前不能直接写成已达成：

1. **生成效率**：同口径 CPU 基准为 `3612.599633 / 3761.787593 = 0.960341x`。系统比 `uniform_rule` 规则采样代理慢约 `3.9659%`。这个代理不是人工规则编辑，因此对“人工编辑 11 倍”只能判为未测，不能说项目达到 0.96 倍人工效率。
2. **实车成本**：当前 CARLA 严格验收墙钟时间为 `12.9075 s`，baseline 为 `13.622 s`，时间代理下降 `5.2452%`。它没有车辆、人工、场地、保险或数据账单，不能换算为“成本降低 90%”。
3. **覆盖率**：项目当前对显式的 `21` 个条件签名覆盖 `21/21 = 100%`；固定模板为 `1/21 = 4.761905%`。这不是行业覆盖率，也不能证明计划书中的“行业不足 15%”。公开资料没有一个可复用的行业统一分母。

## 1. 实车成本的可复核估算

### 1.1 公开资料锚点

| 成本项 | 公开锚点 | 在本项目中的用法 | 边界 |
|---|---|---|---|
| 普通车辆运行/折旧 | BTS 2024 约 `$0.82/英里`，AAA 2024 总拥有和运行成本 `$12,297/年` | 以 `25 mph` 换算为约 `$20.50/车时` 的普通车辆底座 | 不是装有传感器的 AV 测试车报价 |
| 安全员/车辆技师 | BLS 2024 汽车维修技师年薪中位数 `$49,670` | `49,670 / 2,080 = $23.88/时`，再乘 `1.4-2.0` 雇主负担 | 美国职业工资中位数，地区和合同不同 |
| 测试工程师 | BLS 2024 软件开发者年薪中位数 `$133,080` | `133,080 / 2,080 = $63.98/时`，只按 `0.25-1.0` 人时占用计入 | 不是本项目团队实际人工账单 |
| 稀有事件规模 | RAND RR-1478：275 million failure-free miles 示例；8.8 billion miles/约 400 年示例 | 说明单靠真实道路等待极端事件的时间成本 | 统计可行性研究，不是价格 |
| 仿真机会边界 | Mcity 特定混合现实研究报告 1,000 倍、99.99% 里程下降 | 作为外部机会值，不能移植为本项目成果 | 只适用于其研究设置 |

### 1.2 三档运行小时成本模型

以下是为了得到可审计区间而建立的工程模型。除公开锚点外，`传感器/车辆加装系数`、`场地/保险/数据`和工程师占用比例是明确标注的假设，不是外部报价。

公式：

```text
小时成本 = 车辆底座 x AV加装系数
         + 安全员工资 x 雇主负担
         + 工程师工资 x 占用比例 x 雇主负担
         + 场地/保险/能源/数据假设
```

| 档位 | 车辆与传感器 | 安全员 | 工程师占用 | 场地/保险/数据 | 合计估算 |
|---|---:|---:|---:|---:|---:|
| 低 | `$41/h`（`$20.5 x 2`） | `$33/h` | `$22/h`（0.25 人时） | `$50/h` | **约 `$146/h`** |
| 中 | `$72/h`（`$20.5 x 3.5`） | `$40/h` | `$64/h`（0.5 人时） | `$120/h` | **约 `$296/h`** |
| 高 | `$103/h`（`$20.5 x 5`） | `$48/h` | `$128/h`（1.0 人时） | `$250/h` | **约 `$529/h`** |

按一个 **30 分钟实车执行单元** 计算，直接执行成本约为 `$73-$265`，按 `1 USD = 7.2 RMB` 的仅用于展示的换算约为 **￥526-￥1,908/次**。若另有封闭场地租赁、专用保险或多车协同，应在此基础上另加，不能把上表当成场地报价。

按 2,048 个场景、每个场景 30 分钟、尚未计入重复种子和失败重跑，核心运行成本模型约为 **`$149,504-$541,696`**。这是“如果每条都要实车跑一次”的量级估算，不是项目已经节省的金额。

### 1.3 对计划书“降低 90%”的判断

当前不能给出真实节省率。要得到可申报的数字，必须再测一组端到端单位成本：

```text
实车单位成本 = 车辆 + 人员 + 场地 + 保险 + 能源 + 数据 + 失败重跑
仿真单位成本 = 服务器折旧/电费 + 运行时长 + 存储 + 人工审核 + 失败重跑
成本降低率 = 1 - 仿真单位成本 / 实车单位成本
```

公开资料说明了为什么这个比值可能很高，但不替代项目账单。当前最稳妥的状态仍是 `not_assessed`。

## 2. 行业覆盖率与项目内覆盖率

NHTSA、ISO 34502 和 PEGASUS 都把 ADS 安全评估组织成测试案例、ODD 和多层场景数据库；它们没有给出“全行业极端场景总数”以及各企业已覆盖多少的统一公开分母。SUNRISE 的覆盖度论文也显示，超过 200,000 个场景、10 个类别在指定定义下可以得到 100%，说明百分比随参考集和指标变化。

因此，计划书中的“行业不足 15%”目前只能作为**待核实的计划书假设**，不能当作已引用行业事实。

### 2.1 当前项目结果

| 参考分母 | 系统覆盖 | 解释 |
|---:|---:|---|
| 项目 `seed_v1` 的 21 个条件签名 | `21/21 = 100%` | 项目条件覆盖代理，已测 |
| 同一 21 个签名的固定模板 | `1/21 = 4.761905%` | 规则模板对照，不是行业 |

### 2.2 分母敏感性分析

如果未来把项目 21 个签名映射到一个更大的、明确列出的行业参考目录 `D`，项目覆盖率是 `covered / D`，不能继续使用 `21/21` 代替：

| 假设参考分母 `D` | 目前最多覆盖 21 个时的比例 |
|---:|---:|
| 21 | 100% |
| 50 | 42% |
| 100 | 21% |
| 200 | 10.5% |

这张表不是行业估计，而是提醒：**覆盖率的关键不是把分子写大，而是先冻结可追溯的分母**。达到计划书的 90% 需要在同一个目录中覆盖 `0.9D` 个可执行签名，并报告天气、道路、交通参与者、时段和危险事件的分层覆盖，而不只是一个总数。

## 3. “11 倍”当前是多少，为什么没有达到

同一 CPU/Python/15 维范围/Schema 构建和校验契约下：

```text
系统吞吐      = 3,612.599633 条/秒
规则代理吞吐  = 3,761.787593 条/秒
系统/代理     = 0.960341x
相对变化      = -3.9659%
```

这表示当前 LHS 在该微基准上比 `uniform_rule` 慢约 3.97%，不是“达到 0.96 倍人工编辑”。原因是两边都在做机器参数采样；它没有测量人类从规则选择、参数填写、保存、校验、返工到入库的完整操作链。

为了验证“11 倍”，应把实验单位改为完整场景任务，并让至少 3 名有 CARLA 配置经验的人员完成相同任务：

1. 预先冻结 20-30 个场景任务和验收条件。
2. 记录人工从空白到可执行 JSON 的墙钟时间、返工次数和失败率。
3. 记录 Web 系统从表单到合格入库的墙钟时间、失败率和人工确认时间。
4. 以 `有效入库场景数 / 总人时` 计算吞吐，报告中位数、四分位数和每人结果。
5. 只有在同一任务分母下 `system_throughput / human_throughput >= 11` 才能写“达到 11 倍”。

注意：若只拿当前“机器生成一条记录的微秒级耗时”去和人类编辑比较，会人为放大倍率，不能作为计划书验收。

## 4. 优化空间与可验证顺序

### P0：先修正测量对象

- 把生成、Schema 校验、JSONL 写盘、去重、风险排序、入库拆成五段计时；当前只看到总墙钟，无法知道 3.97% 差距来自哪一段。
- 新增完整人工任务计时，解决“11 倍”分母缺失。这比继续优化裸 LHS 更重要。

### P1：提升端到端吞吐

- 参数生成改为 NumPy 批量向量化，减少每条记录的 Python 对象和字符串构造。
- JSONL 使用批量缓冲，最终批次再做完整 Schema/物理约束校验；保留轻量范围预检，不能取消最终质量门。
- 将去重、风险排序和写盘纳入“有效吞吐”，避免只优化一个不代表用户体验的微基准。

### P2：提升覆盖而非只追倍率

- 冻结多层场景参考目录，按天气、道路、交通参与者、时段、危险事件分别计算覆盖。
- 用当前 21 个签名作为回归子集，扩展新的独立签名后再算总体覆盖；生成器采用稀疏区域优先和去重反馈。
- 对 high/critical 只把代理用于候选排序，最终仍由 CARLA 严格验收确认，避免为了覆盖率引入不可执行样本。

### P3：GPU 使用边界

- LHS 和规则采样主要是 CPU 任务，GPU 化未必收益；GMM/CVAE/Diffusion 的批量训练和生成才适合在 GPU1 做对照。
- GPU0 的 vLLM 不动；GPU1 先检查现有 TensorRT 服务和显存，再安排短基准。不要为追求“11 倍”人为加入等待或删掉校验。

## 5. 状态与下一步

| 目标 | 当前状态 |
|---|---|
| 实车成本降低 90% | `not_assessed`；已有公开资料区间和模型，暂无项目账单/实测 |
| 人工规则编辑效率 11 倍 | `not_assessed`；同口径机器规则代理为 `0.960341x` |
| 行业不足 15% -> 极端场景覆盖 90% | `not_assessed`；项目条件覆盖为 `100%`，行业分母缺失 |

推荐下一步按顺序执行：

1. 做 20-30 条场景的人工 vs Web 端到端计时实验，先得到真实效率倍数。
2. 对系统流水线做分段 profiling，再决定 CPU 向量化或 GPU1 批量生成。
3. 建立可追溯场景参考目录，重新计算分层覆盖率；在此之前不改写计划书中的行业 15% 假设。
